# Movie Memory

A small full-stack app: sign in with Google, save your favorite movie, and get a fun fact about it generated by OpenAI.

**Variant chosen: A (Backend-Focused: caching and correctness).**

Stack: TypeScript, Next.js 16 (App Router), React, TailwindCSS, Postgres 16, Prisma 6, Auth.js (NextAuth v5) with Google OAuth, OpenAI API, Vitest.

---

## Which variant and why

I chose **Variant A**. My background is in data engineering and backend work (ETL pipelines, SQL, data warehousing), so correctness under concurrency, data modeling, and failure handling are the problems I find most interesting and can reason about most carefully. Variant A also has a clear, testable correctness target: at most one generated fact per user per 60 seconds, no matter how many tabs or refreshes hit the server at once.

## Setup

### Prerequisites

- Node.js 22 LTS or newer (developed on Node 26)
- Docker Desktop (for local Postgres), or any hosted Postgres such as Neon
- A Google Cloud OAuth client (Web application)
- An OpenAI API key

### 1. Clone and install

```bash
git clone https://github.com/akankshaj2712/Movie-Memory.git
cd Movie-Memory
npm install
```

### 2. Start Postgres

```bash
docker run -d --name moviememory-db -p 5432:5432 \
  -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=moviememory postgres:16
```

If the container already exists: `docker start moviememory-db`.

### 3. Configure Google OAuth

In Google Cloud Console > Google Auth Platform:

1. Configure the consent screen (External) and add your Google account under **Audience > Test users**.
2. Create a **Web application** client with:
   - Authorized JavaScript origin: `http://localhost:3000`
   - Authorized redirect URI: `http://localhost:3000/api/auth/callback/google`

### 4. Environment variables

Copy `.env.example` to `.env` and fill it in:

| Variable | Required | Description |
|---|---|---|
| `DATABASE_URL` | Yes | Postgres connection string, e.g. `postgresql://postgres:postgres@localhost:5432/moviememory` |
| `AUTH_SECRET` | Yes | Random secret used by Auth.js to sign cookies. Generate with `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` |
| `AUTH_URL` | Yes (local) | `http://localhost:3000`. Forces the OAuth callback to use localhost. |
| `AUTH_GOOGLE_ID` | Yes | Google OAuth client ID |
| `AUTH_GOOGLE_SECRET` | Yes | Google OAuth client secret |
| `OPENAI_API_KEY` | Yes | OpenAI API key |
| `OPENAI_MODEL` | No | Defaults to `gpt-4o-mini` |

None of these use the `NEXT_PUBLIC_` prefix, so none are sent to the browser.

### 5. Database migrations

```bash
npx prisma migrate dev      # local: applies migrations and generates the client
npx prisma migrate deploy   # production/CI: applies existing migrations only
npx prisma studio           # optional: browse the data
```

### 6. Run

```bash
npm run dev     # http://localhost:3000 (use localhost, not the Network IP)
npm test        # runs the Vitest suite
```

### Troubleshooting

- **`redirect_uri_mismatch` or "device_id required for private IP"**: open the app at `http://localhost:3000`, not the Network address that `npm run dev` prints. Google settings can also take a few minutes to apply.
- **`401 Incorrect API key provided`**: check whether `OPENAI_API_KEY` is set globally (Windows environment variables or a conda environment). Next.js does not override existing environment variables with values from `.env`.
- **Can't reach database**: make sure the Docker container is running (`docker ps`).

## Architecture overview

### Project structure

```
app/
  page.tsx                      Landing page + first-time/returning redirect
  onboarding/
    page.tsx                    Onboarding screen (first-time only)
    actions.ts                  Server action: validate and save movie
    onboarding-form.tsx         Client form, shows server validation errors
  dashboard/
    page.tsx                    Profile, favorite movie, logout
    fact-card.tsx               Server component that renders the fact
    refresh-fact-button.tsx     Client button that re-renders the page
  api/
    auth/[...nextauth]/route.ts Auth.js handlers (sign in, callback, sign out)
    fact/route.ts               GET /api/fact for the signed-in user
lib/
  facts.ts                      Variant A logic (pure, dependency-injected)
  fact-store.ts                 Prisma implementation + real dependencies
  openai.ts                     OpenAI client (server-only)
  validation.ts                 Movie input schema (zod)
  session.ts                    requireUser() helper
  prisma.ts                     Prisma client singleton
auth.ts                         Auth.js config
prisma/schema.prisma            Data model
tests/
  facts.test.ts                 Cache, burst, failure, authorization tests
  api-fact.test.ts              Route-level authorization tests
```

### Auth and routing flow

1. `/` checks the session with `auth()`.
   - No session: show the landing page with "Sign in with Google".
   - Session, `favoriteMovie` is null: redirect to `/onboarding`.
   - Session, `favoriteMovie` set: redirect to `/dashboard`.
2. Sign-in uses `redirectTo: "/"`, so after Google login every user goes back through step 1. The first-time vs returning decision lives in exactly one place.
3. `/onboarding` and `/dashboard` call `requireUser()`, which redirects to `/` if there is no valid session.

Sessions use the **database strategy**: the browser holds an opaque session token and the session lives in Postgres. Auth checks happen inside server components and server actions rather than middleware, because Prisma does not run on the edge runtime.

### Data model

```prisma
model User {
  id               String    @id @default(cuid())
  name             String?
  email            String?   @unique
  image            String?
  favoriteMovie    String?   // null means onboarding not done
  factGenStartedAt DateTime? // generation lock (lease), see below
  facts            Fact[]
  ...
}

model Fact {
  id        String   @id @default(cuid())
  userId    String
  movie     String   // snapshot of the title at generation time
  content   String
  createdAt DateTime @default(now())
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, movie, createdAt(sort: Desc)])
}
```

Key decisions:

- **`favoriteMovie` being null is the onboarding signal.** No separate `onboarded` flag that could drift out of sync with the actual data.
- **`Fact.movie` is a snapshot.** If a user changes their movie, facts about the old one can never be returned as the cached fact for the new one. The cache key is effectively (user, movie).
- **The composite index matches the hot query exactly**: "latest fact for this user and movie" is an index lookup.
- **Facts are kept as history**, not overwritten. That supports the fallback behavior and keeps a record of what was shown.
- **The generation lock lives on `User`.** There is at most one lock per user, so a nullable timestamp on a row we already read is the simplest correct place for it.

### Fact generation (Variant A)

All logic is in one function, `getFactForUser(userId, deps)` in `lib/facts.ts`. It receives its dependencies (store, OpenAI call, clock, sleep) as arguments, which keeps it free of Prisma and network code and makes it deterministic to test.

```
getFactForUser(userId)
  1. Read the user's movie from the DB (never from the request)
     -> none: return no_movie
  2. Latest fact for (user, movie) is < 60s old?
     -> yes: return it (source: cache)
  3. Try to claim the generation lock (atomic UPDATE)
     -> lost: another request is generating.
              Poll up to 6 x 500ms for a fresh fact -> return it (cache)
              Still nothing: return the stale fact (fallback) or a friendly error
     -> won:
        4. Re-check the cache (a previous lock holder may have just saved one)
        5. Call OpenAI, insert the fact, return it (source: fresh)
        6. On error: return the latest fact even if stale (fallback),
                     otherwise a friendly error
        7. finally: release the lock, but only if it is still ours
```

**Cache window.** A fact is fresh when `now - createdAt < 60_000` ms, so a fact exactly 60 seconds old triggers regeneration. The same clock is used to write `createdAt` and to compare it, which avoids app vs database clock mismatch.

**Burst protection: "generation in progress" flag with a lease.** The lock is claimed with a single conditional update:

```sql
UPDATE "User"
SET "factGenStartedAt" = $now
WHERE id = $userId
  AND ("factGenStartedAt" IS NULL OR "factGenStartedAt" < $now - interval '30 seconds')
```

Why this is safe: when two requests run this at the same time, Postgres row-locks the user row. The second UPDATE waits for the first to commit, re-evaluates its WHERE clause against the new value, and updates 0 rows. Exactly one request sees `count = 1` and generates. This holds across multiple server instances because the coordination happens in the database.

Supporting details:

- **Lease (30s).** If a request crashes while holding the lock, the lock expires on its own, so a user is never stuck. The lease is longer than the worst-case OpenAI time (10s timeout with 1 retry).
- **Re-check after acquiring.** Without it, request B could read a stale cache, request A could finish and release, then B could claim the lock and generate a duplicate.
- **Owner-only release.** Release uses `WHERE factGenStartedAt = <my timestamp>`, so a request whose lease expired can never release a lock that another request now holds.
- **No connection held during the OpenAI call.** The lock is claimed and released in two short statements.

**Failure handling.** OpenAI errors and timeouts are caught. The user gets the most recent saved fact for their movie (even if older than 60s, labeled as a saved fact) or, if none exists, a friendly message. The real error is logged on the server only.

### OpenAI integration

- `lib/openai.ts` imports `server-only`, so the build fails if it is ever imported into client code. The API key is never exposed to the browser.
- 10 second timeout and 1 retry, so a slow API cannot hang the page.
- The client is created lazily, so a missing key breaks only fact generation, not the dashboard.
- The movie title is user input: it is validated, capped at 100 characters, and sent in the user message rather than the system prompt.
- The response is trimmed and rejected if empty. React escapes it on render.
- The 60 second cache plus the lock also cap OpenAI usage at one call per user per minute, regardless of refresh rate.

## Security and correctness

| Requirement | Implementation |
|---|---|
| Validate movie input server-side | `lib/validation.ts` (zod): trims, collapses whitespace, 1 to 100 characters. Enforced in the server action; the input's `maxLength` is only a UX hint. |
| Users cannot access or modify other users' data | The user id always comes from the session, never from a URL, form field, or body. Server actions call `auth()` themselves. Fact queries always filter by `userId`. `GET /api/fact` ignores any `userId` query param (tested). |
| Onboarding is first-time only | Page redirect, plus the DB update only applies `WHERE favoriteMovie IS NULL`. |
| No secrets on the client | No `NEXT_PUBLIC_` variables; OpenAI and Prisma code is `server-only`; errors shown to users are generic. |
| Missing Google photo or name | Avatar falls back to an initial; the name falls back to the email prefix, then "there". |

## Tests

`npm test` runs 12 tests with Vitest.

**`tests/facts.test.ts`** runs the real `getFactForUser` against an in-memory store with a fixed clock:

- Cache: fact at 59s is reused; fact at exactly 60s and at 5 min regenerates; facts for a previous movie are ignored
- Burst: 5 concurrent requests produce exactly one OpenAI call and one stored fact, and all 5 return the same fact
- Failure: stale fact returned when OpenAI fails; friendly error when no fact exists; lock released after a failure
- Authorization: user A never receives user B's fact; a user without a movie gets `no_movie`

**`tests/api-fact.test.ts`** tests the route handler:

- Returns 401 without a session
- Uses the session user and ignores `?userId=` in the URL

## Key tradeoffs

- **Lease-based flag instead of the other options.** An in-memory lock breaks across server instances. A transaction or advisory lock would hold a DB connection open for the whole OpenAI call. A unique constraint on a 60 second bucket uses fixed windows (12:00:00 to 12:00:59) that do not match the sliding "60 seconds since the last fact" rule.
- **Waiting requests poll for up to 3 seconds.** If OpenAI is slower than that, they get the stale fact or a friendly error rather than waiting longer. Fine for a fun fact; a real-time channel would be overkill.
- **Movie stored as free text, no Movie table.** There is no stable ID to normalize against without an external catalog.
- **App clock instead of database `now()`.** Simpler and testable with an injected clock. With several app servers, clock skew could shift the window slightly; using Postgres `now()` for both write and compare would fix that.
- **Unit tests use an in-memory store that mirrors the Prisma store's semantics** rather than a real database. Fast and deterministic, but the atomic UPDATE itself is verified by reasoning and manual testing, not by an automated test.
- **Database sessions instead of JWT.** Sessions can be revoked by deleting a row and no user data lives in the cookie. The cost is a DB lookup per `auth()` call and no edge middleware.

## What I would improve with 2 more hours

1. **Integration test against a real Postgres** that fires concurrent requests, to prove the atomic lock under true concurrency.
2. **Use Postgres `now()`** for the cache window to remove any dependency on app server clocks.
3. **Avoid repeated facts** by passing the last few facts into the prompt.
4. **Edit favorite movie** from the dashboard (the cache already invalidates correctly because facts are keyed by movie).
5. **Movie normalization** through a catalog API (e.g. TMDB) and a `Movie` table, so "the matrix" and "The Matrix" share facts.
